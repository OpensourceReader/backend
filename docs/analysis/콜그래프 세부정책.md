# 콜 그래프 세부 정책_V1

## 0. 목적과 분석 범뮈
- 본 문서는 콜 그래프(Call Graph)를 **디버깅 및 코드 이해를 돕는 사용 흐름 분석 도구**로 활용하기 위한 세부 정책을 정의합니다.  
- 정책은 1. 메서드 수집, 2. 콜그래프 연결과 3. 콜그래프 조회 세가지로 나뉘어집니다.
- 외부 JAR까지는 콜그래프를 만들지 않고 external 표시로 처리합니다.

---

## 1. 메서드 수집 방법
### 1.1 수집 대상
- 메서드 수집은 **바이트코드(.class)** 를 기준으로 수행합니다.
    - 소스코드로 하면 import문으로 케이스를 나누면서 가져올 수 있으나 타입이 정해진 중간 결과물을 사용하는 것이 
    - "콜그래프 정확도 및 자바버전에 따른 유지보수"에 유리해서 컴파일된 바이트코드를 사용합니다.
- JVM 실행 단위로 존재하는 모든 메서드를 분석 대상으로 포함합니다.
  - 다만, 소스코드에 존재하는 메서드인지 컴파일러가 생성해준 바이트코드에만 존재하는 (합성/브릿지/생성) 메서드인지 구분합니다.

### 1.2 수집 데이터 보강
- 소스코드 AST 분석을 통해 메서드의 startLine, endLine 정보를 보강합니다.

---

## 2. 식별 규칙
### 2.1 클래스 식별자
- 클래스는 "classInternalName"으로 구분합니다. 
- 모듈마다 중복된 classInternalName이 있을 수도 있으나 같은 classInternalName을 사용하면 하나는 무시되기에
- 정상적인 설계로 이뤄진 레포라면 중복된 classInternalName을 사용하지 않는 걸로 가정합니다.
### 2.2 메서드 식별자
- 연결을 할떄, (메서드 이름 + 리턴타입 + 메서드 파라미터 타입)을 메서드 시그니처로 다룹니다.
- 컴파일에서는 메서드 이름, 메서드 파라미터 타입으로 구분하지만
- 바이트코드는 bridge, self 메서드 떄문에 메서드 시그니처에 리턴타입도 넣어야합니다.

## 3. Type Graph를 우선적으로 생성합니다.
메서드 연결(콜그래프)을 수행하기 전에,클래스/인터페이스 간의 상속 및 구현 관계(Type Graph)를 먼저 구성합니다.

1. 각 타입(.class)은 자기 자신이 선언한 상속 정보만을 기준으로,
   - `extends`로 지정한 상위 클래스
   - `implements` 또는 `extends`로 지정한 인터페이스를 Type Graph에 연결합니다.
2. 자바와 같이 다형성을 지원하는 언어에서는
   - 메서드 해석 시 상속 및 인터페이스 계층을 재귀적으로 탐색해야 하므로, 해당 관계를 사전에 그래프로 구축해 둡니다.
3. Type Graph는 메서드 자체를 연결하기 위한 목적이 아니라, 이후 단계에서
    - 상위 클래스(super chain) 탐색
    - 인터페이스 구현체 탐색
    - root class / origin contract 탐색을 효율적으로 수행하기 위한 **탐색 인덱스**로 사용됩니다.

## 4. CodeMethod 타입 종류
1. INTERNAL_DECLARED
    -  source(AST)에 동일 시그니처 선언 존재
2. INTERNAL_GENERATED
    - source(AST)엔 없고, bytecode(.class)에는 동일 시그니처 존재
3. INTERNAL_INHERITED_RESOLVED
    - 현재 클래스 declared 없고, super/interface(default 포함) 탐색으로 “내부 타입”의 선언 메서드를 찾음
4. INTERNAL_INHERITED_DECLARATION
    - 현재 클래스에 declared는 없고, 호출은 내부에서 발생했으며, 상속/계약 관계상 상위 타입에 선언이 존재해야 하지만, 상위 타입이 외부 라이브러리여서 선언 owner를 내부 엔티티로 특정할 수 없는 경우
5. EXTERNAL_RESOLVED
    - callsite owner가 외부 타입이거나, callee owner가 외부로 확정되며, 내부 선언 엔티티 불가
    - 예: String.valueOf, List.add (static/virtual 구분 안 하기로 했으니 여기로 통일)
6. OTHER : 기타등등(기록용)

### 5. 콜그래프 도메인 용어정리
- Outgoing : 현재 메서드에서 사용하는 메서드들을 나타냅니다.
- Ingoing : 현재 메서드를 사용하는 메서드들을 나타냅니다.
- Declared method : 해당 타입(.class)에 “직접 선언된” 메서드
- Inherited method : 상위 타입에서 선언되었고, 하위타입이 물려받은 메서드
- Origin contract : 해당 메서드가 “처음으로 선언된 인터페이스”. 계약의 의미적 출처
    - 이때, origin contract는 계약의 출처를 의미한다. callsite owner(예: I2.m)는 호출 표현상의 타입으로서 별도로 유지한다.
    - 따라서, origin contract는 하나일 수 있으나, callsite owner는 상속 구조에 따라 여러 형태(I0.m, I1.m, I2.m)로 나타날 수 있다.
- Callsite owner : 바이트코드(invokeinterface)에 나타나는 호출 타입, I0.m, I1.m, I2.m 등으로 표현될 수 있음
- 실행 후보들 : execution candidates
    - 클래스 Declared method
    - 상위 클래스 Declared method
    - 인터페이스 default method

## 6. 콜그래프 연결 정책
### 6.1 Outgoing 연결 정책 (Caller → Callee)
### 6.1.1 기본 규칙
- 현재 클래스에 Declared method가 있으면 즉시 연결 : INTERNAL_DECLARED
### 6.1.2 현재 클래스에 선언이 없는 메서드 호출
1. 분류 케이스
   - (A) 상속(Inherited: class): 자식 클래스가 override 하지 않고 부모(super)의 메서드를 그대로 호출/사용하는 경우
     -  예: Child에는 m() 소스가 없고 Parent.m()이 존재
   - (B) default(Inherited: interface): 클래스 체인에 없고 인터페이스 default 메서드가 제공되는 경우
   - (C) runtime-bound(framework): JpaRepository/CrudRepository처럼 인터페이스 계약만 있고 구현은 런타임(프록시/빈 생성)에서 위임되는 경우
### 6.1.3 처리 순서
1. 클래스 상속 체인 우선: super를 따라 동일 시그니처의 선언을 찾고, 발견 시 callee를 해당 상위 클래스 메서드로 수정하여 outgoing을 연결한다. ex)caller -> Parent.m
   - 내부 클래스에서 선언발견 : super 체인 타고 Parent에서 선언을 찾고 “Parent.m으로 수정해서 연결
     - INTERNAL_INHERITED_RESOLVED
   - 부모클래스가 외부라이브러리 클래스인 경우 
     - 소스코드에서 사용된 메서드고 선언된 클래스도 내부에 있지만, 부모 클래스(인터페이스)가 외부라이브러리여서 선언클래스를 특정하지 못하는 경우 -> ex)opensourceRepo(extend Jpa).save()
       - INTERNAL_INHERITED_DECLARATION
     - 소스코드에서 사용된 메서드지만, 선언된 클래스가 외부에 있어, 선언클래스를 가져오지 못하는 경우 -> ex) String.valueOf(), List.add()
       - EXTERNAL_RESOLVED
2. 인터페이스 default 탐색: 클래스 체인에 없을 때만 인터페이스 그래프를 탐색하여 가장 가까운 default provider를 후보로 연결한다.
   - 클래스 상속하고 default메서드랑 겹치면, 상속 클래스 우선, default는 넣지 않는게 맞음
   - 상속에서 없으면 인터페이스 디폴트 메서드에서 구현체를 사용하는게 있는지 찾아야함
   - 없으면, INTERNAL_INHERITED_DECLARATION
### 6.1.4 예시 (설명용, 규칙 아님)
```java
// 상속
class Parent {
    void m() {}
}

class Child extends Parent {
// m() 선언 없음 (inherited)
}

class Client {
    void g() {
        Child c = new Child();
        c.m();          // ✅ 여기서 호출됨 (callee는 사실 Parent.m)
    }
}
```
```java
interface I {
    default void m() { System.out.println("I"); }
}
    
class Parent {
    public void m() { System.out.println("Parent"); }
}
    
class Child extends Parent implements I {
// m() 없음
}

class Client {
    void f() {
      new Child().m();   // 출력: Parent  
    }
}
```

### 6.2. Ingoing 연결 정책 (Callee → Callers)
- 구현체에서 다형성이 적용가능한 선언타입들을 연결합니다.
#### 6.2.1  인터페이스 Ingoing 조회 방식
- 구현체 후보를 callee로 연결합니다.
  - origin contract(Parent)와 execution candidates 한 화면에서 다보여줍니다.
  - 이떄 다음 흐름으로 연결하려면 구현체중 하나를 누르고, 다음화살표를 클릭해야합니다.
#### 6.2.2  Ingoing이 필요한 이유
- 아래 상황을 대비하여 연결합니다. Outgoing만 저장하면, 다형적 호출(인터페이스/상속)의 실제 실행 후보로 이어지는 흐름이 끊깁니다.
  - callsite owner가 인터페이스이거나
  - callsite owner가 상위 클래스(추상/비최종 클래스) 인 경우
#### 6.2.3 기본 원칙
- 다형성이 없는 메서드는 Outgoing 기반 조회로 충분(나중에 저장된 간선으로 호출)
- 다형성이 있는 경우에만 Ingoing 그래프를 구성한다
#### 6.2.4 인터페이스 호출 Ingoing 규칙(인터페이스/상속 다형성을 활용 가능한 클래스 탐색, 소스코드(구현체)내에 메서드가 있는 경우)
1. 클래스 Declared method 우선
   - 해당 메서드는 클래스의 Declared method로 간주한다.
   - 현재 클래스에 override가 있으면 해당 메서드를 실행 기준으로 삼음
2. origin contract 탐색
   - 인터페이스 extends 그래프를 상향 탐색
   - 동일 origin contract를 extend한 모든 인터페이스 연결
     - I.o -> C
     - I2.o -> C
     - I3.o -> C
3. 클래스 상속 체인 탐색 :
   - 상속 관계에서 메서드가 override 된 경우, 런타임 호출은 항상 가장 구체적인 구현체(concrete class) 로 디스패치된다.
     - 상속 관계에서 메서드가 override 된 경우, 런타임 호출은 가장 구체적인 구현체로 디스패치되므로 현재 구현체 기준으로 상속 원본(root)을 찾는다.
   - root class가 나오면 해당 클래스를 extend하는 모든 클래스들을 현재 클래스와 연결한다.
   - 상속+인터페이스가 섞여있을 경우도 있다.
     - 같은거 있으면 둘다 연결, 둘다 탐색해야함
4. 외부 라이브러리의 메서드여서 탐색이 불가능할떄
   - 못 찾았다!, 그러면 INTERNAL_INHERITED_DECLARATION로 CodMethod 생성

#### 6.2.4 예시 (설명용, 규칙 아님)
```java
// 최상위 계약 (origin contract)
public interface I {
  void o();
}
// I 를 상속
public interface I2 extends I {
}

// I2 를 상속
public interface I3 extends I2 {
}

public class C implements I3 {
    @Override
    public void o() {
        System.out.println("C.o()");
    }
}
```

## 7. 콜그래프 조회 정책
### 7.1 기본 필터 옵션
- private 메서드
- <init>, <clinit>
- java/ 등 JDK 패키지
- EXTERNAL_RESOLVED / OTHER

### 7.2 조회 원칙
- 필터는 연결 결과를 변경하지 않는다
- 오직 표현(UI/응답) 에만 영향을 준다
