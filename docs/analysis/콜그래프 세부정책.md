# 콜 그래프 세부 정책

## 0. 목적과 분석 범뮈
- 본 문서는 콜 그래프(Call Graph)를 **디버깅 및 코드 이해를 돕는 사용 흐름 분석 도구**로 활용하기 위한 세부 정책을 정의합니다.  
- 정책은 1. 메서드 수집, 2. 콜그래프 연결과 3. 콜그래프 조회 세가지로 나뉘어집니다.
- 외부 JAR까지는 콜그래프를 만들지 않고 external 표시로 처리합니다.

---

## 1. 메서드 수집 방법
### 1.1 수집 대상
- 메서드 수집은 **바이트코드(.class)** 를 기준으로 수행합니다.
    - 소스코드로 하면 import문으로 케이스를 나누면서 가져올 수 있으나 타입이 정해진 중간 결과물을 사용하는 것이 
    - "콜그래프 정확도 및 자바버전에 따른 유지보수"에 유리해서 컴파일된 바이트코드를 사용합니다.
- JVM 실행 단위로 존재하는 모든 메서드를 분석 대상으로 포함합니다.
  - 다만, 소스코드에 존재하는 메서드인지 컴파일러가 생성해준 바이트코드에만 존재하는 (합성/브릿지/생성) 메서드인지 구분합니다.

### 1.2 수집 데이터 보강
- 소스코드 AST 분석을 통해 메서드의 startLine, endLine 정보를 보강합니다.

---

## 2. 식별 규칙
### 2.1 클래스 식별자
- 클래스는 "classInternalName"으로 구분합니다. 
- 모듈마다 중복된 classInternalName이 있을 수도 있으나 같은 classInternalName을 사용하면 하나는 무시되기에
- 정상적인 설계로 이뤄진 레포라면 중복된 classInternalName을 사용하지 않는 걸로 가정합니다.
### 2.2 메서드 식별자
- 연결을 할떄, (메서드 이름 + 리턴타입 + 메서드 파라미터 타입)을 메서드 시그니처로 다룹니다.
- 컴파일에서는 메서드 이름, 메서드 파라미터 타입으로 구분하지만
- 바이트코드는 bridge, self 메서드를 구분하기 위해 메서드 시그니처에 리턴타입도 넣어야합니다.

---

## 3. Type Graph를 우선적으로 생성합니다.
메서드 연결(콜그래프)을 수행하기 전에,클래스/인터페이스 간의 상속 및 구현 관계(Type Graph)를 먼저 구성합니다.
간선(Edge)을 저장한후 조회시 인접리스트로 반환합니다.

1. 각 타입(.class)은 자기 자신이 선언한 상속 정보만을 기준으로,
   - `extends`로 지정한 상위(super) 클래스
   - `implements` 또는 `extends`로 지정한 인터페이스를 Type Graph에 연결합니다.
2. 자바와 같이 다형성을 지원하는 언어에서는
   - 메서드 해석 시 상속 및 인터페이스 계층을 재귀적으로 탐색해야 하므로, 해당 관계를 사전에 구축해 둡니다.
3. Type Edge는 메서드 자체를 연결하기 위한 목적이 아니라, 이후 단계에서
    - 상위 클래스(super chain) 탐색, 인터페이스 구현체 탐색, root class / origin contract 탐색을 효율적으로 수행하기 위한 **탐색 인덱스**로 사용됩니다.

## 4. CodeMethod 타입 종류
1. INTERNAL_DECLARED
    -  source(AST)에 동일 시그니처 선언 존재
2. INTERNAL_GENERATED
    - source(AST)엔 없고, bytecode(.class)에는 동일 시그니처 존재
3. INTERNAL_INHERITED_RESOLVED
    - 현재 클래스 declared 없고, super/interface(default 포함) “내부 타입”의 선언 메서드를 활용하는 경우
4. INTERNAL_INHERITED_DECLARATION
    - 현재 클래스에 declared는 없고, 호출은 내부에서 발생했으며, 상속/계약 관계상 상위 타입에 선언이 존재해야 하지만, 상위 타입이 외부 라이브러리여서 선언 owner를 내부 엔티티로 특정할 수 없는 경우
5. EXTERNAL_RESOLVED
    - callsite owner가 외부 타입이거나, callee owner가 외부로 확정되며, 내부 선언 엔티티 불가
    - 예: String.valueOf, List.add (static/virtual 구분 안 하기로 했으니 여기로 통일)
6. OTHER : 기타등등(기록용)

### 5. 콜그래프 도메인 용어정리
1. 그래프 CUD 관련 용어
   - Dispatch: 계약(contract) → 실행 후보(concrete)
   - Ingoing: 사용하지 않음(혼동 방지)
   - Outgoing : 현재 메서드에서 사용하는 메서드들을 나타냅니다.
   - Declared method : 해당 타입(.class)에 “직접 선언된” 메서드
   - Inherited method : 상위 타입에서 선언되었고, 하위타입이 물려받은 메서드
   - Origin contract : 해당 메서드가 “처음으로 선언된 인터페이스”. 계약의 의미적 출처
       - 이때, origin contract는 계약의 출처를 의미한다. callsite owner(예: I2.m)는 호출 표현상의 타입으로서 별도로 유지한다.
       - 따라서, origin contract는 하나일 수 있으나, callsite owner는 상속 구조에 따라 여러 형태(I0.m, I1.m, I2.m)로 나타날 수 있다.
2. 조회 관련 용어
- Callsite owner : 바이트코드(invokeinterface)에 나타나는 호출 타입, I0.m, I1.m, I2.m 등으로 표현될 수 있음
- execution candidates(실행 후보들)
    - 클래스 Declared method
    - 상위 클래스 Declared method
    - 인터페이스 default method

## 6. 콜그래프 연결 정책
- 다형성을 사용했을떄에 어떤 클래스에서 메서드가 활용되는지의 기준
### 6.1 Dispatch 연결 정책 (Contract → Execution Candidates)
- 다형적 호출에서 **선언 타입(contract)** 과 **실행 후보(concrete implementations)** 를 명시적으로 연결하여, 호출 흐름이 계약 지점에서 끊기지 않고 실행 후보까지 이어지도록 합니다.
- 또한, **런타임 디스패치 가능성에 대한 해석 결과를 보완**하는 역할을 합니다.
- **다형성이 없는 호출**
    - Outgoing(call-site) 기반 조회로 충분
- **다형성이 있는 호출**
    - Dispatch 그래프를 구성한다
        - 인터페이스 호출
        - 상속 기반 가상 호출 등
#### 6.1.1  인터페이스/상속 Dispatch 조회 방식
- **선언(contract) 메서드**를 기준으로 **실행 후보(implementations)** 를 연결한다.
- 한 화면에서 다음을 함께 표시한다:
    - **Origin contract** (인터페이스/상위 클래스 선언)
    - **Execution candidates** (구현체 메서드들)
- 조회화면에서 다음 흐름으로 진행하려면: 후보 중 하나를 선택 → 다음 화살표 클릭
#### 6.1.2 Dispatch 연결이 필요한 사례
- **Outgoing(call-site)만 저장**할 경우, 다형적 호출에서 **실제 실행 후보로의 흐름이 단절**될 수 있다.
- 특히 다음 경우에 발생한다:
    - callsite owner가 **인터페이스**인 경우
    - callsite owner가 **상위 클래스(추상 / 비최종 클래스)** 인 경우
#### 6.1.3 인터페이스 / 상속 Dispatch 규칙(메서드 기준)
- 탑다운 : 미리 만들어둔 Type Graph룰 바탕으로, 자신을 extends/implements 하는걸 찾아서 연결합니다.
1. 인터페이스 케이스(implements/extends)
   1. 자신을 implements하는 구현체를 찾습니다. 인터페이스에서 이어지는 "첫번쨰 구현체(바로 implement한 구현체)"까지 찾습니다.
      - 첫번쨰 구현체에서 다시 extends하는 하위 구현체는 이 단계에서 고려하지 않습니다.
   2. 자신을 extends하는 인터페이스를 Type Graph에서 찾습니다.
      - extends하는 인터페이스의 명세에 본인의 메서드를 추가합니다. 그리고 상위 인터페이스 명세(메서드)와 하위 인터페이스 명세(메서드)를 연결합니다.
      - extends하는 인터페이스에서 (1)의 과정-첫번쨰 구현체까지 찾는 과정을 되풀이 합니다.
      - 자신을 extends/implements 하는 인터페이스가 더이상 나오지 않을떄까지 반복합니다줌
   3. 첫번쨰 구현체를 찾으면, 구현체에서 implement한 인터페이스의 명세(메서드)와 구현체의 메서드를 연결합니다.  
   4. default메서드의 경우 고려필요
      1. 하위 인터페이스는 메서드 추가해서 넣어놓기, 디폴트 메서드는 하위 인터페이스에서 override를 할 수 있으니, 이 경우도 상속케이스의 로직을 따릅니다.
      2. 하위 클래스에서는 상속케이스의 로직을 따릅니다.
2. 상속 케이스(클래스 상속) 
   - 자신을 extends하는 자식 구현체를 찾습니다. 
     - 위 과정은 자식 구현체가 더이상 존재하지 않을떄까지 반복합니다.
   - 만약 부모 클래스의 메서드를 자식클래스가 override 했다면, 
     - 다형성을 사용했을떄 자식 클래스의 메서드가 사용되므로 자식클래스의 메서드에서 부모 메서드를 연결합니다. 
   - 만약 부모 클래스의 메서드를 자식클래스가 override 하지 않았다면, 
     - 다형성을 사용했을떄 부모 클래스의 메서드가 사용되므로 자식클래스에 새로운 메서드를 만들어서 연결을 하되, 부모 메서드이고 어디 부모메서드에서 왔는지 표현합니다.

#### 6.1.4 예시 (설명용, 규칙 아님)

1. 인터페이스 대표 케이스
    ```java
    // 최상위 계약 (origin contract)
    public interface I {
      void o();
    }
    // I 를 상속, 메서드 저장시 o를 추가
    public interface I2 extends I {
    }
    
    // I2 를 상속
    public interface I3 extends I2 {
    }
    
    public class C implements I3 {
        @Override
        public void o() {
            System.out.println("C.o()");
        }
    }
    ```
2. 상속 케이스들(클래스 상속)
    ```text
     - 부모 -> 자식1(no override) override 안했으면 부모가 쓰입니다.
     - 부모 -> 자식1(no override) override 했으면 자식이 쓰입니다.
     - 부모 -> 자식1(no override) -> 자식2(override) override 했으면 자식꺼 쓰는게 맞는데
        - 이러면 자식2의 부모인 자식1하고 연결을 해주는게 아니라 부모에서 연결을 해줘야 되는데, 자식1에서는 메서드가 없어서 연결하려며 부모를 찾아야함
        - 이럴바에는 자식1에도 메서드를 저장하고, 대신에 부모 메서드라는걸 표시해주자, 조회에서는 필터링 가능하도록, 그리고 어떤 부모인지도 적어줘야함
    ```

### 6.2 Outgoing 연결 정책 (Caller → Callee)
### 6.2.1 기본 규칙
- 현재 클래스에 Declared method가 있으면 즉시 연결 : INTERNAL_DECLARED
### 6.2.2 현재 클래스에 선언이 없는 메서드 호출
1. 분류 케이스
   - (A) 상속(Inherited: class): 자식 클래스가 override 하지 않고 부모(super)의 메서드를 그대로 호출/사용하는 경우
     -  예: Child에는 m() 소스가 없고 Parent.m()이 존재
   - (B) default(Inherited: interface): 클래스 체인에 없고 인터페이스 default 메서드가 제공되는 경우
   - (C) runtime-bound(framework): JpaRepository/CrudRepository처럼 인터페이스 계약만 있고 구현은 런타임(프록시/빈 생성)에서 위임되는 경우
### 6.2.3 처리 순서
- Callee가 외부 클래스(등록되지않는 클래스)여서 연결할 수 없는 경우
  - external로 메서드 생성해서 연결
- 등록된 클래스 내부에 메서드가 없는데 사용되었을 경우
  1. 부모클래스의 케이스 
     1. 부모 클래스에 구현이 있는 경우(조상(위로 여러 단계)에 구현이 있는 경우) -> dispatch에서 연결됨, 외부 라이브러리가 아닌 이상
     2. 부모클래서의 메서드가 abstract이고, abstract가 선언만 갖는 경우
        1. 자식클래스가 abstract이면, 상속 받는다고해도 상관없음 
        2. 자식클래스가 concrete이면 구현체가 있어야함
  2. 인터페이스 default 메서드를 사용한 경우
     1. 외부라이브러리의 인터페이스가 아닌 이상 dispatch전략에서 메서드를 추가하는 방향으로 결정
- 결론은 메서드가 없으면
    - 타입이 있으면, 외부프레임워크를 사용했다고 판단해서 INTERNAL_INHERITED_DECLARATION 처리
    - 타입이 없으면, 외부메서드(EXTERNAL_RESOLVED) 처리
  - 메서드가 있으면, 바로 연결 

### 6.2.4 예시 (설명용, 규칙 아님)
```java
// 상속
class Parent {
    void m() {}
}

class Child extends Parent {
// m() 선언 없음 (inherited)
}

class Client {
    void g() {
        Child c = new Child();
        c.m();          // ✅ 여기서 호출됨 (callee는 사실 Parent.m)
    }
}
```
```java
interface I {
    default void m() { System.out.println("I"); }
}
    
class Parent {
    public void m() { System.out.println("Parent"); }
}
    
class Child extends Parent implements I {
// m() 없음
}

class Client {
    void f() {
      new Child().m();   // 출력: Parent  
    }
}
```

## 7. 콜그래프 조회 정책
### 7.1 기본 필터 옵션
- private 메서드
- <init>, <clinit>
- java/ 등 JDK 패키지
- EXTERNAL_RESOLVED / OTHER

### 7.2 조회 원칙
- 필터는 연결 결과를 변경하지 않는다
- 오직 표현(UI/응답) 에만 영향을 준다
